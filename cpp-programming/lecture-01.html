Lesson 1 asks: “The screen says 42. Good. What does this prove?”

The operative question

Producing an answer is the tempting proxy

One build has finished and one path has produced one value. That is an observation. It may be useful evidence, but it is not yet an account of the computation. It says nothing about an empty input, an invalid state, a much larger workload or a resource that was never released. The program may still be appropriate. The point is that the displayed answer has not established it.

Typing source code was never the whole responsibility. The programmer decides what the program should do, identifies the states that may exist, controls the changes that are permitted, and judges whether the available evidence supports the claim being made. An AI system, a library or a colleague may provide an implementation. None of them removes that responsibility from the person who accepts it.

Appropriateness is a judgement

The judgement is earned by connecting five things: a requirement, a model of state, an implementation, proportionate evidence and a conclusion that remains within the limits of that evidence. If one link is vague, the conclusion must remain bounded. Source that appears polished cannot repair an absent requirement. A large test suite cannot establish a property that nobody stated. A fast demonstration cannot define the workload that matters.

What must be true?

Turn a wish into observable behaviour and explicit constraints.

What state exists?

Name the values and the valid transitions between them.

Who is responsible?

Give each invariant and important resource a clear owner.

What may vary?

Hide volatile detail without hiding policy or consequence.

What counts as evidence?

Decide how the claim will be challenged before the convenient case becomes persuasive.

From values to method

Seven rules become seven review questions

A principle becomes operational when it changes what we inspect. Each rule therefore earns a question that can be asked of the running program rather than merely admired on a poster. The full rule statements below are retained from Lesson 1; the questions are the lecture’s review prompts.

1 · Be capable of estimating the timeliness of your computation

Which path threatens which stated resource budget?

2 · Understand what a program is actually doing in a computational sense

Where can invalid state enter, and who prevents it?

3 · Use automated and human-based approaches to evaluate correctness

What does this evidence justify, and where does it stop?

4 · Utilise existing program code and expertise

Which contract are we trusting when we rely upon this component?

5 · Realise value and worth

Which useful consequence has changed for the user or the system?

6 · Be capable of spotting and nurturing fellow computer programmers

Can another programmer understand and extend the decision safely?

7 · Ensure that gaining an appropriate solution is a by-product of an enjoyable journey

Did the evidence challenge the model, or does it support retaining it?

The recurring course model

The memory account

This is a language-level account, not an exact diagram of bytes in a particular build. Later lectures will add addresses, storage duration, layout and ownership without pretending that the first diagram knows more than it does.

  1. Name
  2. Type
  3. Object
  4. Stored state
  5. Derived state
  6. Valid states
  7. Permitted changes
  8. Responsibility
  9. Lifetime
  10. Evidence

For each example we ask the same questions. What object exists? Which value does it actually store? Which observations can be calculated from that value? Which states are valid? Which operation may change the state? Who owns the rule? For how long does the object exist? What evidence supports the account?

The account is intentionally modest. The C++ language tells us that the example below contains an int data member called points_. It does not entitle this lecture to announce a universal byte size, physical address or layout for every implementation. Precision includes refusing to claim the detail that has not been established.

The worked development

Health as controlled state

Suppose a small game gives the player health. It must start between zero and one hundred. Damage must never increase it or take it below zero. Other code needs to ask how many points remain and whether the player is alive. Calling this “just an integer” discards the very information that must direct the design.

Invariant: while a PlayerHealth object is valid, 0 <= points <= 100.

Stored state, class-wide policy and derived state

Each PlayerHealth object contains one non-static int data member called points_, and that member stores the health value. The name maximum describes class-wide policy; it is not a separate per-object health value. The function alive() derives an answer from points_; the object does not need to store a second flag and keep two values in agreement.

This is a language-level account. It deliberately makes no universal claim about an exact byte size or physical location. Those matters depend upon details that have not been fixed here and will be treated when the course has the machinery to treat them honestly.

#include <algorithm>
#include <cassert>
#include <iostream>
#include <stdexcept>

class PlayerHealth {
public:
    static constexpr int maximum = 100;

    explicit PlayerHealth(int initial) : points_{initial}
    {
        if (initial < 0 || initial > maximum) {
            throw std::out_of_range{"health must be between 0 and 100"};
        }
    }

    [[nodiscard]] int points() const noexcept { return points_; }
    [[nodiscard]] bool alive() const noexcept { return points_ > 0; }

    void take_damage(int amount)
    {
        if (amount < 0) {
            throw std::invalid_argument{"damage cannot be negative"};
        }
        points_ = std::max(0, points_ - amount);
    }

private:
    int points_;
};

int main()
{
    PlayerHealth health{10};
    std::cout << "start: " << health.points() << '\n';

    health.take_damage(3);
    assert(health.points() == 7);
    std::cout << "after 3 damage: " << health.points() << '\n';

    health.take_damage(20);
    assert(health.points() == 0);
    assert(!health.alive());
    std::cout << "after 20 damage: " << health.points() << '\n';
}

Trace every transition

The source is not the trace. The trace is the account of what exists before the operation, which condition is checked, which stored value changes and what remains true afterwards.

Construction is also a transition

Before PlayerHealth health{10};, there is no completed health object. The constructor receives a requested initial value and checks it. With 10, construction completes and a valid object becomes available. With an invalid value, the constructor throws and no completed PlayerHealth object emerges from that construction. Describing the failed case as an object containing invalid health would therefore be the wrong state account.

The invalid request is a reasoned case

The shown main function does not call take_damage(-2). The table includes that case because the method has explicit failure behaviour which belongs in the model. It must not be presented as output that the shown program produced. The assignment is not reached, so the existing object’s state is unchanged when the exception is thrown. Handling determines whether surrounding execution can continue and observe that unchanged object; it does not determine whether the assignment occurred.

The boundary earns its place

The class gives one component responsibility for one invariant. Callers request a domain operation instead of assigning representation directly. Failure is detected near its cause. The representation can later change without forcing every caller’s source to change, provided the public promise remains stable. A layout change can still require recompilation or break a binary interface. These are reasons for the boundary, not permission to ignore that boundary.

The word private is ordinary C++ access control. It prevents normal direct access from code that lacks permission; it is not a universal memory-safety barrier. The class is appropriate here because all permitted health changes share a rule. If the data had no shared rule, a class could add ceremony without protecting anything.

Evidence before confidence

What do the output and assertions establish?

The expected output and assertions support selected observations in this one example. They do not convert selected observations into proof of every future state transition.

start: 10
after 3 damage: 7
after 20 damage: 0

This supports: construction with 10, one transition from 10 to 7, one transition from 7 to 0, and the derived observation that zero is not alive.

This does not yet support: every permitted initial value, invalid construction, execution of the negative-damage case, every sequence of future calls or behaviour in the larger game.

assert is useful development evidence, but a build may remove its checks when NDEBUG is defined. A requirement that must be enforced in every supported build cannot depend solely upon an assertion remaining active.

Requirement and invariant

State what must be preserved before an observation can be interpreted.

Boundary examples

Exercise zero, one hundred, excessive damage and invalid requests deliberately.

Properties and analysis

Explore broader input spaces and inspect lifetime, bounds and undefined-behaviour risks.

Human review

Challenge the requirement, ownership decision, interface and readability with context.

Relevant measurement

Measure only when a stated workload and resource budget make the cost consequential.

Bounded conclusion

Say: this evidence supports this property under these conditions.

Minutes 47–50 · transfer

Account for the state before you improve the code

Consider the deliberately weak representation struct Health { int points; };. Do not begin by decorating it with syntax. First write four things:

  1. the valid-state rule;
  2. the permitted transitions, including rejected requests;
  3. the component responsible for preserving the rule; and
  4. the evidence that would challenge the convenient example.

Now ask which value the object must actually store and which answers can be derived. Ask whether the proposed boundary prevents a real error or merely changes the appearance of the source. Ask what happens before construction, after failure and when the object’s lifetime ends. The implementation follows those decisions. It cannot substitute for them.
